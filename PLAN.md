# Sales and Purchase Management System: Development Plan

This is the working plan for building the system described in [scope.md](scope.md). We build it one module at a time, and each module ships with its backend and frontend together. A module is not done until its API, screens, tests and acceptance checklist are all complete.

---

## 1. Reference products and what we take from each

| Product | What we model | Why |
|---|---|---|
| **Zoho Books** (primary) | Module structure, document lifecycles (statuses), form fields, list page with a detail pane beside it, record-payment screen, credits flow, recurring invoice profiles | The scope is based on Zoho Books, and its sales and purchases flows are the most complete in this class of software |
| **Xero** | Dashboard simplicity (cash position and money owed shown first), status tabs with counts on the invoice list, a clean and uncluttered form | It rates consistently higher than QuickBooks for ease of use and setup |
| **QuickBooks Online** | Quick actions on list rows (for example, "Receive payment" directly from an invoice row), overdue reminders | These cut the clicks needed for daily work |
| **Invoice Ninja** (open source) | Data model for linking payments and credits to invoices (`paymentables`: one payment covers many invoices, with `amount` and `refunded` tracked per link) and the balance fields on invoices and clients | A real, working schema we can check our design against |

Rules adopted from Zoho Books (confirmed in its help docs):

- **Quote statuses:** Draft → Sent → Accepted / Declined → Invoiced. Only an Accepted quote can be converted to an invoice.
- **Invoice statuses:** Draft, Sent, Partially Paid, Paid, Overdue, Void.
- **Payments received:** one payment can be split across several unpaid invoices of the same customer. Any amount not applied is saved as an *excess payment*, which can be applied to a later invoice or refunded.
- **Credit note statuses:** Draft, Open, Closed (all credit used), Void. Credit is applied to invoices using "Apply Credits" or refunded.
- **Recurring invoices:** a *profile* (name, customer, frequency, start and end date, items) generates invoices, either as drafts or already marked sent.
- **Sales receipts:** a sale and its payment recorded together (customer, items, payment mode, reference number). No receivable is created.
- **Expenses** are always *paid* (there is a "Paid Through" field). Zoho records amounts owed to vendors with **Bills**, not expenses. See Decision 2 in section 10.

## 4. Architecture and conventions

### 4.1 API conventions
- Base path: `/api/v1`.
- Lists: `GET /invoices?q=&status=overdue&customerId=&dateFrom=&dateTo=&page=1&pageSize=25&sort=-date`
  → `{ data: [...], meta: { page, pageSize, total } }`
- Errors: `{ error: { code: "INVOICE_HAS_PAYMENTS", message, details } }` with correct HTTP status codes.
- State changes are separate action endpoints, not generic PATCH requests:
  `POST /quotes/:id/mark-sent`, `/accept`, `/decline`, `/convert-to-invoice`
  `POST /invoices/:id/mark-sent`, `/void`, `/apply-credits`
  `POST /credit-notes/:id/open`, `/void`, `/refunds`
  `POST /recurring-invoices/:id/stop`, `/resume`

### 4.2 Money and quantities
- Database: money `NUMERIC(18,2)`, quantity `NUMERIC(18,3)`, tax rate `NUMERIC(6,3)`.
- All calculations use `decimal.js` inside `packages/shared`. The browser shows live totals with the **same function** the server uses to store them, so the two can never disagree.
- Single base currency (set in Settings). Multi-currency is out of scope.

### 4.3 Calculating document totals (quotes, invoices, receipts, credit notes, recurring profiles)
Discount and tax are applied **per line**, following Zoho's "discount at line item level" option. This avoids having to spread a document-level discount across lines.

```text
line.gross     = quantity × rate
line.discount  = gross × discount%   OR a fixed amount
line.amount    = gross − discount                 (tax is calculated on this)
line.tax       = round2(line.amount × taxRate)
subtotal       = Σ line.amount
taxTotal       = Σ line.tax (also grouped by tax name for display)
total          = subtotal + taxTotal + shipping + adjustment   (adjustment can be negative)
```

### 4.4 Balances and statuses: one source of truth
- `invoice.amountPaid = Σ payment allocations + Σ credits applied`
- `invoice.balanceDue = total − amountPaid`
- The stored lifecycle is `draft | sent | void`. The displayed status is derived from it:
  `void` → Void · `draft` → Draft · balance = 0 → **Paid** · 0 < balance < total → **Partially Paid** · dueDate < today → **Overdue** · otherwise **Sent**
- Any change that touches an invoice balance calls `InvoiceBalanceService.recalculate(id)` **inside the same database transaction**.
- "Overdue" is computed when data is read (`balance > 0 AND due_date < current_date`), so no nightly job is needed.
- Customer balances are **computed by queries, never stored**, so they cannot drift out of sync:
  - Outstanding receivables = Σ balanceDue of non-void, non-draft invoices
  - Unused credits = Σ unused amounts on payments + Σ open credit note balances

### 4.5 Integrity rules
- Every money-changing operation runs in one DB transaction. Invoice rows are locked (`SELECT … FOR UPDATE`) while payments or credits are applied.
- Document numbers come from a `number_series` row per document type (prefix plus a zero-padded counter), incremented with `UPDATE … RETURNING` so two users can never get the same number.
- **Drafts can be deleted. Sent financial documents can only be voided**, so the audit trail stays complete.
- Quotes have no financial effect, so they stay deletable until they are converted to an invoice.
- A document with payments or credits applied cannot be voided until they are removed.
- An invoice cannot be edited so that its total falls below the amount already paid.
- Customers, vendors and items that are used in transactions are marked **inactive** instead of being deleted.

### 4.6 Permissions and audit
- Permission keys are `module:action`, for example `invoices:create`, `invoices:void`, `reports:view`, `settings:manage`.
- Seeded roles: **Admin** (everything), **Accountant** (all transactions and reports, no user management), **Sales** (customers, items, quotes, invoices, receipts, payments), **Viewer** (read only). Admins can edit roles.
- The backend enforces permissions. The frontend hides actions the user is not allowed to take.
- `audit_logs`: user, action, entity, entity id, before/after diff (JSON), IP address, timestamp. Written for create, update, status change, void and delete on transactions and settings. Each document's detail page shows it as a **History** panel.

## 5. Data model (overview)

```text
SYSTEM        users >─ roles (one role per user; its permissions are a list on the role)
              refresh_tokens · audit_logs · attachments
              organization (profile, base currency, date format, fiscal year, timezone)
              number_series · payment_terms · taxes · payment_modes · expense_categories

CONTACTS      contacts (type: customer | vendor, business | individual, display name,
                        company, email, phones, payment_term, opening_balance, status)
              contact_persons · contact_addresses (billing | shipping)

ITEMS         items (type goods | service, name, sku, unit, selling_price, sales_description,
                     cost_price, purchase_description, tax_id, preferred_vendor_id,
                     track_inventory, reorder_level, status)
              stock_movements (item, quantity ±, source_type, source_id, date)

SALES         quotes ─< quote_lines                     quote → invoice (invoice.quote_id)
              invoices ─< invoice_lines                 invoice.recurring_profile_id
              recurring_invoice_profiles ─< recurring_invoice_lines
              sales_receipts ─< sales_receipt_lines
              payments_received ─< payment_allocations >─ invoices
              credit_notes ─< credit_note_lines        credit_note.invoice_id (reference)
              credit_applications (credit_note → invoice, amount, date)
              credit_refunds · payment_refunds

PURCHASES     expenses (date, category, amount, tax, payment_mode, vendor?, reference,
                        notes, receipt attachment)
              [Decision 2 = A] bills ─< bill_lines · payments_made ─< bill_payment_allocations
```

Line items are stored in **separate line tables**, not as JSON like Invoice Ninja does. Reports such as "Sales by Item" need to query individual lines.

Stock tracking is optional per item. Stock goes down when an invoice becomes *sent* or a sales receipt is saved, and back up when a credit note is marked as a return. Stock on hand is `Σ stock_movements`.

## 7. Build order: module by module

Every module goes through the same steps (see section 8). Size: S = small, M = medium, L = large.

### Module 0: Foundation (M)
**Setup:** `git init`, Node 25 (works; Prisma prints a notice that it is not an officially supported version), pnpm installed globally (Node 25 no longer ships corepack), the PostgreSQL 16 server already running on this machine with the `spms` and `spms_test` databases, `.env` files, Prettier, Vitest.
**Backend:** NestJS app, Prisma connection, config module, global error filter, Zod validation pipe, pagination helper, Swagger, health endpoint.
**Shared:** package wiring, money helpers, `calculateDocumentTotals()` with unit tests (rounding, negative adjustment, 0% tax, fixed and percentage discounts).
**Frontend:** Next.js app, Tailwind, shadcn/ui, TanStack Query, app shell (sidebar, top bar), `DataTable`, `PageHeader`, `StatusBadge`, form building blocks, toasts, empty states, 404 page.
**Done when:** `pnpm dev` starts the API and web app, the shell renders, and the shared totals tests pass.

### Module 1: Authentication, users, roles and settings (L)
**Backend:** login, refresh, logout, current user; users CRUD (admin creates users with a temporary password, deactivates users); roles and permissions CRUD; `PermissionsGuard`; login rate limiting; audit log service; organization profile (logo upload); number series; payment terms; taxes; payment modes; expense categories; seed (admin user, roles, default terms, taxes, payment modes).
**Frontend:** login page, protected routes, current-user menu, change password; Settings area with Organization, Users, Roles, Taxes, Payment Terms, Payment Modes, Expense Categories, Transaction Numbering and Preferences (date format, currency symbol).
**Done when:** each role sees only what it is allowed to, and changing a number series prefix shows up on the next document created.

### Module 2: Customers (M)
**Backend:** `contacts` with type customer, contact persons, billing and shipping addresses, search (name, company, email), filters (active/inactive), mark inactive, balance query endpoint.
**Frontend:** list, create/edit form (Business/Individual, display name suggestions built from name and company, addresses with "copy billing to shipping", contact persons), detail page with Overview. The Transactions and Statement tabs fill in as later modules land.
**Done when:** a customer can be created, searched, edited and made inactive, and changes appear in History.

### Module 3: Items (M)
**Backend:** items CRUD, goods or service, sales and purchase information, default tax, optional stock tracking with opening stock, stock adjustment endpoint, `stock_movements`, search for pickers (active items only).
**Frontend:** list (with stock-on-hand column when tracking is on), form with Sales Information and Purchase Information sections, detail page with a stock movements list, and an `ItemSelect` component for documents.
**Done when:** items appear in the picker with their rate and tax filled in, and stock adjustments update stock on hand.

### Module 4: Quotes (L). Builds the shared document engine.
**Backend:** `documents/` shared services (numbering, line validation, totals, status helpers); quotes CRUD, mark sent, accept, decline, convert to invoice (the invoice write path is stubbed until Module 5; the conversion is fully wired there); clone; expiry date.
**Frontend:** `LineItemsEditor`, `TotalsPanel`, `DocumentPreview`, `SplitListLayout` (all reused later); quote list, form, detail and print view.
**Done when:** a quote's totals match between the browser, the API and the stored values, status changes follow the rules, and the quote prints cleanly.

### Module 5: Invoices (L)
**Backend:** invoices CRUD, payment terms → due date, mark sent (decrements stock), void (blocked if payments exist), clone, displayed-status logic including Overdue, status tab counts, **quote → invoice conversion** (copies lines, sets the quote to Invoiced), `InvoiceBalanceService`.
**Frontend:** list with status tabs, form, detail with print preview, a print route with `@media print` styles (browser Print or Save as PDF), "Create invoice" button on an accepted quote, invoices shown on the customer's Transactions tab.
**Done when:** Quote → Invoice works end to end, overdue shows correctly, void rules are enforced, and a printed invoice fits on A4/Letter.

### Module 6: Payments Received (L)
**Backend:** record payment with allocations to invoices (validated: same customer, not void, amount ≤ balance, Σ allocations ≤ amount), recording a payment against a draft marks it sent, excess saved as unused amount, apply unused amount to an invoice later, refund excess, edit or delete a payment (recalculates invoices), row locking.
**Frontend:** record payment screen (section 6.5), list, detail (receipt preview, invoices paid), "Record payment" on the invoice detail page and list row, payments on the customer's Transactions tab, receivables and unused credits cards on the customer Overview.
**Done when:** partial payment → Partially Paid, full payment → Paid, overpayment → excess that can be applied to the next invoice, deleting a payment restores the invoice balances, and the customer balance is correct after each step.

### Module 7: Credit Notes (M)
**Backend:** CRUD with optional reference invoice, create from invoice (prefilled), Draft → Open, apply to one or more invoices, refund, balance and Closed status, void, "return to stock" option.
**Frontend:** list, form, detail (applications and refunds), "Apply credits" dialog on the invoice detail page when credits are available, "Create credit note" in the invoice More menu.
**Done when:** Customer → Invoice → Credit Note → Apply reduces the invoice balance and closes the credit note when used up, and refunds work.

### Module 8: Sales Receipts (S), reusing the document engine
**Backend:** CRUD with payment mode and reference, decrements stock, void, clone. Not included in receivables.
**Frontend:** list, form (document form plus a payment section), detail and print.
**Done when:** receipts count toward sales but never create an outstanding balance.

### Module 9: Recurring Invoices (M)
**Backend:** profiles (name, customer, frequency: weekly / monthly / yearly / every N days, weeks or months; start date; end date or never expires; payment terms; lines; create as Draft or as Sent), statuses Active / Stopped / Expired, stop and resume, daily cron job that generates due invoices **idempotently** (unique `profile_id + period_date`), next-run calculation (month-end safe: 31 Jan → 28/29 Feb), "Create invoice now" action.
**Frontend:** list (next invoice date, status), form, detail with the child invoices it generated.
**Done when:** a job run over a simulated date range creates exactly the expected invoices, and running it twice creates no duplicates.

### Module 10: Vendors (S), reusing contacts
**Backend:** contacts with type vendor, the same features as customers, vendor transactions query.
**Frontend:** list, form and detail, with Transactions showing expenses (and bills if chosen).
**Done when:** vendors are fully managed and linked from expenses and items (preferred vendor).

### Module 11: Expenses (M)
**Backend:** CRUD (date, category, amount, tax, payment mode, vendor, reference, notes, receipt upload), filters (date range, category, vendor, payment mode), totals endpoint.
**Frontend:** list with a totals row, form with receipt drop zone, detail with receipt preview, expenses on the vendor's Transactions tab.
**Done when:** filtered totals match the sum of the rows shown, and receipts upload and preview.

### Module 11b: Bills and Payments Made (M). Only if Decision 2 = A.
This mirrors Invoices and Payments Received on the purchase side, so it reuses most of that code. It provides real amounts owed to vendors and a Vendor Balances report.

### Module 12: Dashboard (M)
**Backend:** `GET /dashboard/summary?period=` returns all figures from SQL aggregates in a single request.
**Frontend:**

2. Zod schemas and enums in `packages/shared`

8. The module's "Done when" checklist walked through by hand
9. A commit, tagged `module-N`

### Main flows that must always keep working (Playwright)
1. Customer → Quote → Accept → Invoice → Partial payment → Full payment
2. Customer → Invoice → Credit Note → Apply → Invoice paid
3. Overpayment → excess applied to the next invoice
4. Recurring profile → job run → invoices generated
5. Vendor → Expense → included in the dashboard and Expenses by Vendor report
6. A Viewer role cannot create or void anything

## 10. Decisions (settled 15 September 2026)

1. **Stack:** Next.js (web) + NestJS (API) + PostgreSQL, TypeScript throughout, as detailed in section 2.
2. **Amounts owed to vendors:** option A. Module 11b adds Bills and Payments Made, mirroring Invoices and Payments Received.
3. **Inventory:** optional per-item stock tracking is included in v1.
